## Delivered contracts (exactly as on the branch)

### `App\Notifications\Alerts\ResponsibleInactiveScanner implements Scanner`
```php
public function scan(CarbonImmutable $now): int;
```
Reads every inactive employee **once** into an in-memory collection keyed by id — never a `whereHas` across connections (contracts §10, `.ai/rules/alerts.md`) — then selects open projects (`ProjectStatus::isOpen()`) whose `user_id` is in that set, in one query, and sends one notification each. HR unreachable returns 0 rather than throwing: a scanner that cannot read HR should be quiet, not noisy.

**The ledger stage is `employee:<id>`, not a date.** That one choice is what gives D-62's "once per person per record" without storing anything:

| What happens | What the scanner does |
|---|---|
| it runs again | silent — the same stage is already claimed |
| the owner is changed to another person who has left | **raises again**, under the new employee id |
| the owner is changed to somebody still here | silent — the project leaves the query |
| the person comes back (HR sets `is_active`) | silent, same reason |

Registered in `config/notifications.php` under `scanners.daily`.

### `EventCatalog`
`proposal.responsible_inactive`, module `proposals`, priority `now`, type `scanner`, exactly as the `[contract]`.

> **One key, two subject types.** The contract files it under `proposals`, but this half's subject is a *project*, so the payload is sent with module **`projects`** — otherwise `RecipientFilter` would gate a project notification behind the proposal permission, and the link would lead somewhere the reader may not be allowed. The catalog entry keeps the contract's module. Flagged for Dev 1: once W-34a lands, two keys may read better than one.

### `QuickActions`
`project.reassign`, offered on a `project` subject when the owner is inactive, redirecting to the project page. It only opens the page — D-62 asks a person to choose, so nothing is reassigned automatically — and the project form re-checks before anything is saved.

**Offered to holders of `projects.update` *or* `proposals.update`**, which the prompt allows ("`proposals.update` (or `projects.update`) holders"). Not a nicety: the Public Relations Manager is who the alert tells and holds `proposals.update` but **not** `projects.update`, so requiring the latter would have sent the recipient a notification they could not act on. Caught by the test, not by reading.

### Recipients
`Public Relations Manager` holders, via `RecipientResolver::usersWithRoles()`.

The contract also names the "proposal owner (creator)". A project has no such person — its owner **is** the one who left — so the project half tells the PR Manager alone. The proposal half should add the creator when W-34a lands.

### Language
`lang/{en,ar}/notifications.php`: `alerts.responsible_inactive.project` (names the record and the person), `events.proposal.responsible_inactive.{title,body}`, and the quick-action label `quick.labels.project_reassign` — "Reassign" / «إعادة التعيين». No money anywhere.
