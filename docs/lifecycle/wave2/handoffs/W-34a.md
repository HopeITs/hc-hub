### `App\Actions\Proposals\SaveProposal` — `$data['locations']`
```php
locations?: list<array{city_id: int|string|null, program_id?: int|string|null, responsible_employee_id?: int|string|null,
                       center_ids?: list<int|string>, is_new?: bool|int|string|null, new_program_name_en?: ?string, new_program_name_ar?: ?string}>
```
- **Create:** `locations` and `projectIds` are each `required_without` the other; a form may send either or both. Each `projectIds` entry becomes a row through `LinkProposalProject` (below); the sent rows are then merged on top. Messages: `locations.required_without` → `proposals.locations_required`, `projectIds.required_without` → `proposals.link_at_least_one_project` (so both keys carry an error when nothing is sent).
- **Edit:** `locations` is optional; when sent it must be a non-empty array (`proposals.locations_required`) and replaces the rows; when omitted the rows are untouched.
- **Row rules** (checked in the validator's `after` hook, HR read once per rule, centers from the in-memory lookup):

| Error key | Rule | Message |
|---|---|---|
| `locations.{i}.city_id` | positive id of an **active** HR city | `proposals.location_choose_the_city` |
| `locations.{i}.city_id` | `(city_id, program_id)` distinct across the set; one "no program" row per city | `proposals.location_city_duplicate` |
| `locations.{i}.program_id` | exists in `programs` (when sent) | `proposals.location_choose_the_program` |
| `locations.{i}.center_ids` | every center's `city_id` = the row's city (`HrCenter::remembered`) | `proposals.location_center_not_in_city` |
| `locations.{i}.responsible_employee_id` | an HR employee with `is_active = 1` (when sent) | `proposals.location_responsible_inactive` |
| `locations.{i}.new_program_name_en` / `_ar` | required when `is_new` and no `program_id` | `proposals.location_program_name_required` |

- **Replacement** (`App\Support\ProposalLocationRows::replace(Proposal $locked, array $rows, User $actor): array{added, removed, changed}`, inside the proposal transaction under the lock): rows are matched by `(city_id, program_id)`. Removed keys are deleted (centers and a pending request cascade) **unless the row carries a `project_id`** (link-owned rows survive a replacement; only `UnlinkProposalProject` removes them). Kept rows are updated (responsible, `is_new`, centers, request names); new keys are inserted; `sort` follows the sent order, leftover project rows after. A row with a project is never `is_new`. A new row without a program creates its `program_requests` row (`requested_by` = actor); a kept row whose request is no longer needed drops the pending request.
- **After commit:** when the counts are not all zero, one activity `proposal.locations_changed` on the proposal with `{added, removed, changed}` and `ProposalLocationsChanged::dispatch(...)` with the same counts (ShouldDispatchAfterCommit). A refused save writes and dispatches nothing. Counts only, never names or amounts.

### `LinkProposalProject` / `UnlinkProposalProject` (signatures unchanged)
After the pivot write: `ProposalLocationRows::attachProject($locked, $project)` fills the row waiting on the project's `(city_id, program_id)` (sets `project_id`, `is_new = false`, adds the project's `center_id`, keeps the row's responsible, drops a pending request) or inserts a new row (`responsible_employee_id = projects.user_id`, which is an HR employee id). A second project on the same city and program (another center) is merged into the existing row as a center; the row keeps its first project. Unlink deletes the rows with that `project_id`. Both record `proposal.locations_changed` and dispatch the event (counts), in addition to `proposal.project_linked|unlinked`.

### Slice 2 · requirement keys, materialiser, recipients

**Keys.** `ProposalTransitions`: `concept note → concept note review` = `['locations', 'donor', 'planned_dates']`. `TransitionProposal::unmetRequirement()` knows `locations` (`$proposal->locations()->exists()`, message `proposals.locations_required`) and `locations_complete` (message `proposals.locations_incomplete`). The one definition of completeness is `App\Support\ProposalLocationRows::incompleteRowIds(Proposal): list<int>`: a row is complete when `program_id` and `responsible_employee_id` are set, it carries a `project_id` **or** at least one center, and its program request (if any) is not `pending`. A proposal with no rows is complete (pre-W-34a fixtures still approve). `linked_project` is still checked by `ApproveProposal` on the union after materialisation (`proposals.link_project_first`), for one release.

**`ApproveProposal`** (signature unchanged), inside its transaction: lock → `approve` gate → status assertion → `locations_complete` refusal → `MaterialiseProposalLocations::handle($locked, Auth::id())` → lock the linked projects (now including the new drafts) → `linked_project` refusal → donor input validation → proposal + note + event → `ApproveProjectFromProposal` over the union. A refused input or a failing outer transaction rolls the created projects back. `ApprovalResult::$warnings` = the materialiser's warnings, then `no_agreement`.

```php
App\Actions\Proposals\MaterialiseProposalLocations   (final; SaveProject + LinkProposalProject promoted)
  handle(Proposal $proposal, int $actorId): MaterialisationResult   // own transaction + proposal lock when called alone; Gate approve; Gate projects.create when a draft must be created
  preview(Proposal $proposal): MaterialisationResult                // Gate view; reads only
  const WarningLinkedExisting = 'location_linked_existing'
App\Support\MaterialisationResult (readonly): list<int> $createdProjectIds, list<int> $linkedProjectIds, list<int> $waitingLocationIds, list<string> $warnings
```
Per row in `sort, id` order: `project_id` set → skipped; `program_id` null → `waitingLocationIds` (the key already refused the approval, so this is reached only by a direct call); else **one project per center** (a row with no center is refused by the key). For each center: `Project::openProjectFor($centerId, $cityId, $programId)` → the open project is linked through `LinkProposalProject` (`linkedProjectIds`, warning once) else a draft is created through `SaveProject::handle(null, ['centerId', 'programId', 'userId'], $actor)` (name «Program — Center», no dates, **no sectors**, owner assignment pending as on the form) and linked (`createdProjectIds`). `LinkProposalProject` → `ProposalLocationRows::attachProject()` writes `project_id` / `is_new = false` on the row; a second project of the same row joins it as a center (slice 1's merge), so the row keeps its **first** project id. Owner = the row's responsible when they manage a program, else `programs.manager_id` of the row's program; neither → `ValidationException` under `locations_complete` with `proposals.location_owner_required` (`:city`), nothing written. `preview()` returns the same lists before anything exists: `createdProjectIds` holds the **row id** per project that would be created (counts only for the modal).

**Authorization.** `approve` on the proposal (as `ApproveProposal`); `projects.create` on the actor only when a draft must be created (`SaveProject` demands it). Since W-34a Financial holds `projects.create` too (§8, `config/access-control.php`; `php artisan permissions:sync` adds it on an existing environment), so every role that may approve can materialise. A user with `proposals.update` alone gets a 403 and nothing is written when rows would create projects, and still approves rows that only reuse open projects or already carry one.

**`SaveProject`** (Q2): on create, `sectorIds` is required only when the key is sent (the form always sends it); a caller that omits it (the materialiser) creates the project without sectors and `SyncProjectSectors` is not called.

**Recipients.** `Slots::holderOf('hr_liaison')` reads `notification_settings` `hr_liaison_position` (config default null; constant `Slots::HrLiaison`). `ProposalRecipients`: `program_request.opened` → direct = the HR liaison holder (permission-exempt), watchers = Financial + Public Relations Manager as for every proposal event; `program_request.linked` → direct = the proposal owner (`projectOwnerIds()`, permission-exempt). `ActivityParameters` passes the `name` property through, so the sentences' `:name` shows the typed program name.

**Lang (slice 2):** `proposals.approval_warning_location_linked_existing` (the toast for the warning; slice 3 shows it beside `approval_warning_no_agreement`), `proposals.location_owner_required`, en + ar.

## Deviations from contracts.md / the prompt
None to `contracts.md` beyond the `[contract]` text. Choices made in plan review (approved with the plan):
1. **Q1 · `projectIds` stays accepted on create** (`required_without:locations`) until slice 3 removes the picker; every linked project yields a row. Needed so the current form and `CloneProposalForRenewal` keep working.
2. **Q2 · Program request names:** `W-34.md` §1 (`name_en`, `name_ar`, both required) over the prompt's free-text `requested_name`; input keys `new_program_name_en` / `new_program_name_ar`.
3. **Q3 · Event payload:** `W-34.md` §4's `(proposalId, actorId)` plus the prompt's diff counts.
4. **Q4 · `proposal.locations_changed`** registered as a digest catalog key (oversight all, no direct recipients) so the "every movement is a key" rule holds; `program_request.opened|linked` registered now with generic sentences, recipients wired in slice 2.
5. **Q5 · Program requests are guarded by `programs.update`** (`programs.manage` from `W-34.md` §5 does not exist in §8 or `config/access-control.php`).
6. **Q6 moot:** `projects.user_id` already holds an HR employee id, so the backfill copies it straight into `responsible_employee_id`.
7. **Link-owned rows survive a replacement** (not in the spec): a set sent without the row of a linked project does not delete that row; unlinking does. Keeps `project_proposal` and the rows in step without a second way to unlink.
8. **Two projects on one (city, program) of a proposal** (two centers): the unique index allows one row, so the second project is merged in as a center and the row keeps its first `project_id`. Local data has no such pair today (checked). Slice 2's materialiser must decide the row→projects mapping for multi-center rows (`W-34.md` §1 "one project per center"); flagged under Follow-ups.
9. **Slice 2 (plan review 2026-11-04, Q1–Q8):** owner of a materialised draft = the responsible if they manage a program, else the program's manager, else refused (`SaveProject` admits only program managers as owners); drafts start without sectors (`SaveProject` requires a sector only when `sectorIds` is sent); **Financial gains `projects.create`** (§8, Dev 1 2026-11-04) so every approver can materialise; an approver without it is still refused with a 403 before anything is written; a row without a project needs a center to be complete (no host-center rule exists for rows); one project per center with one responsible per row (the schema allows nothing else); PR Manager = the watcher role, HR mailbox = the `hr_liaison` slot (§9 line added); a pending program request blocks approval (contract over the prompt's "still approves"); `preview()` fills `createdProjectIds` with row ids.
