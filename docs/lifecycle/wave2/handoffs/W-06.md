### `App\Actions\Proposals` — the two writers of `on_hold_since`
```php
final class SetProposalOnHold {
    /** @param array{reason: string, remind_on: string} $input */
    public function handle(Proposal $proposal, ProposalStatus $expectedStatus, array $input): ProposalStatusNote;
}
final class ClearProposalOnHold {
    public function handle(Proposal $proposal, ProposalStatus $expectedStatus, ?string $note = null): ProposalStatusNote;
}
```
Both follow `TransitionProposal`'s shape: `Gate::authorize('update', $locked)`, one `DB::transaction`, the row reloaded with `lockForUpdate()`, the status compared with `$expectedStatus` and refused with `proposals.stale_status`, and exactly one `proposal_status_notes` row carrying the **current** status with `kind` = `on_hold` / `off_hold`. **Neither writes `status`.** Set is refused outside `submitted` / `concept note submitted` (`proposals.hold_only_while_submitted`), needs a `reason`, and takes `remind_on` as `after:today` (`proposals.remind_on_future`). Clear on a proposal that is not held is a no-op that still writes its note, so a double click costs one timeline line.

Both authorize the **logged-in** user, not a passed actor: a test calling them directly needs `actingAs` first.

## Deviations from contracts.md / the prompt

1. **`DeadlineCatalog` and `StalledScanner` were changed although the prompt does not mention them.** Both excluded `on hold` by status. After the migration a held proposal is `submitted`, so leaving them alone would have **restarted stalled and deadline alerts on held proposals** — the opposite of what a hold is for. Both now exclude `whereNull('on_hold_since')`, which preserves today's behaviour exactly. Flagged rather than done silently: **Dev 1 should confirm this reading of D-58.**
2. **`kind` carries all six cases, not the four W-06 uses** (approved in plan review), so W-07 and W-08 find the enum ready.
3. **`ProposalStatus::live()` now excludes `OnHold`.** The prompt only says to deprecate the case; this one line is what removes it from every picker, filter and chart, since §1 already requires those to iterate `live()`.
4. **Slice 1 only** (approved in plan review), hence the merge warning above.
