# I14 · Stock-take audits

Phase P4 · Model: sonnet · Group G · Needs: I07 · Decisions: D7

## Goal
Twice a year IT walks through a center with a phone, ticks every device it finds, and the hub shows what is missing
or damaged — instead of trusting that the sheet is still true.

## Sources of truth
1. `docs/inventory/contracts.md §2 (audits), §5, §6, §7`.
2. A checklist-style page in the hub that saves row by row (Hr checklists) for the interaction pattern.
3. `.ai/rules/pages.md`, `ui.md`, `views.md`, `database-migrations.md`. Handoffs `I05.md`, `I07.md`.

## Start state
- Assets, custody Actions and `ReportAssetCondition` exist.

## Rules
- `StartAudit(city, ?center)`: one open audit per city+center at a time; snapshots as items every non-terminal asset
  located there (including those held by employees of that center). Assets InTransit away are excluded.
- `RecordAuditItem`: result Found / Missing / Damaged + note; the asset must belong to this audit (BOLA). Recording
  is repeatable until the audit closes (last write wins, `checked_by/at` updated).
- `CloseAudit`: requires every item to have a result, or an explicit "mark the rest as missing" confirmation.
  On close, in one transaction: Found → `last_verified_at/by` set; Missing → `ReportAssetCondition(Missing)`;
  Damaged → `ReportAssetCondition(Broken)`. A closed audit is immutable.
- "Found but not on the list" is handled by search-and-add: an asset from another location can be added with result
  Found and a note; it does **not** move the asset (a transfer does) — it is listed in the close summary as a discrepancy.

## Build order
