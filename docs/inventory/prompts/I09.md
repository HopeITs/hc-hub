# I09 · HR bridge

Phase P2 · Model: sonnet · Group E · Needs: I07, I08 · Decisions: D2 · Slices: 2

## Goal
HR and Inventory tell one story. Delivering an onboarding checklist line hands over a real asset; the employee
profile shows current and past equipment; offboarding cannot close while equipment is still held; a handover /
clearance form can be printed.

This is the one task allowed to edit `modules/Hr` — only the files named below.

## Sources of truth
1. `docs/inventory/contracts.md §2 (custodies.checklist_id), §3 (bridge relations), §5`.
2. `modules/Hr/Models/Checklist.php`, `modules/Hr/Actions/Checklists/*`, `modules/Hr/Support/Checklists/ChecklistWorkflow.php`,
   `modules/Hr/Support/**/OffboardingJourneys.php` (equipment-returned step), the employee profile page and its tab registry,
   `ModuleRegistry::addSubjectLinks` and how Hr `registerCoreBridge()` attaches cross-module pieces.

4. `.ai/rules/models-concerns.md`, `models.md`, `database-migrations.md`, `providers.md`, `pages.md`, `views.md`.
5. Handoffs `I07.md`, `I08.md`.

## Start state
- Custody Actions exist. `checklists` has no `asset_id`.

## Slice 1 — checklist ↔ custody
- Migration (in `modules/Inventory/database/migrations`): `checklists.asset_id` nullable FK → `inventory_assets` (nullOnDelete), named index.
- On the Hr deliver step, an optional "pick device" select lists `InStock` assets of the matching category in the
  employee's city (visible to the actor). When chosen, the deliver Action calls `AssignAsset(..., checklistId: $id)`
  inside the same transaction and stores `asset_id`; brand/model/serial on the checklist row are filled from the asset.
- On the Hr receive-back step, a checklist with `asset_id` calls `ReturnAsset` on the linked open custody.
- A checklist without an asset keeps today's behaviour exactly (existing Hr tests stay green, unedited).
- Inventory must stay optional for Hr: Hr code reaches Inventory through one small contract/bridge class bound in
  `InventoryServiceProvider`, not through direct `use Modules\Inventory\…` scattered in Hr actions.
- Tests `tests/Feature/Inventory/Hr/ChecklistCustodyBridgeTest.php`: deliver with asset opens a custody; deliver
  rolls back fully when the asset is not assignable; receive closes the custody; flow without asset unchanged;
  run the existing `tests/Feature/Hr/*Checklist*` files too.

## Slice 2 — profile tab, offboarding, print
- Employee profile → "Equipment" tab (visible with `inventory.view-all`/`view-city` in scope, or to the employee
  themself): current custody + history, link to each asset.
- Offboarding "equipment returned" step is complete only when the employee has no open custody; the step lists what is still held.
- Print view "Handover / clearance form": employee, date, table of devices (tag, item, serial, condition), signature
  lines; bilingual, A4, uses the existing print layout. Route `inventory.employees.custody-form` guarded by the same rule as the tab.
- Tests `EmployeeEquipmentTabTest.php`, `OffboardingEquipmentStepTest.php`: scope/BOLA on the tab and the print
  route; step blocked with an open custody, passes after return.

## Definition of done
- New test files and the existing Hr checklist/offboarding tests pass (paste the lines).
- Handoff lists every Hr file edited, with a one-line reason each.

## Stop and escalate
- The offboarding step is computed in a place that cannot call the bridge without a wider Hr refactor.
- Any existing Hr test must change to pass.

## Do not
- Rename or drop checklist columns, migrate `employee_items` (I11), or edit Hr files beyond those the plan lists.
